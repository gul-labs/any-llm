Opt-in prompt and response storage (ADR-038), and a breaking change to `drizzleUsageSink`'s options.

By default nothing changes and the full prompt and response text is not stored (the `llm_calls` row still carries the model's tool-call arguments, reasoning text and error message, as before). `ClientConfig.payloads?: { redact?, maxChars?, include? }` turns storage on for a client. Every attempt that reached the provider adapter, success or failure, then hands the sink a payload next to its record: `UsageSink.record(record, { payload, logger })` (a sink must declare `acceptsPayloads: true` to be handed one). The payload is the request as sent (system, messages as `{ role, parts }`, text verbatim, tool-call arguments and tool-result values as JSON, tools by name and schema hash; an inline media part is its media type, size and SHA-256, never the bytes) and the raw model text or the attempt's error message. Core's `redactSecrets` patterns run on every string (nested ones too), then your `redact`, then the size caps, last: `maxChars` per string (default 200,000, cut with `[truncated]`) and `4 x maxChars` for the whole payload (the largest strings become a marker first). A payload that cannot be built (a throwing `redact`) is dropped with an `llm.call.payload.dropped` warning and never fails the call. `generate(request, { storePayload: false })` and `runStructured(callSite, vars, { storePayload: false })` opt a call out.

`@gullabs/drizzle` adds the `llm_call_payloads` table (`attempt_id` primary key and foreign key to `llm_calls` with `ON DELETE CASCADE`, `request` and `response` JSONB, `created_at` indexed), `purgeLlmCallPayloads(db, { olderThan })`, `deleteLlmCallPayloads(db, { callIds })` (by call id only: `externalId` can repeat across tenants, so there is no delete by it) and `assertLlmCallPayloadsSchema(db)`. `@gullabs/testing`'s `RecordingSink` keeps the payloads it receives on `payloads` (a `Map` by `attemptId`).

What hosts must change:

- **`drizzleUsageSink` takes an options object.** `drizzleUsageSink(db, table?)` is gone; write `drizzleUsageSink({ db })`. The custom `table` argument is removed and the `InsertableDb` type with it. `db` must be a Drizzle Postgres database with `transaction` (node-postgres, postgres-js, PGlite, ...). A record without a payload is one `INSERT`; a record with a payload is written in a transaction: the ledger row, then the payload row behind a savepoint. A payload failure rolls back to the savepoint, is logged as `llm.call.payload.failed` and the ledger row commits; a ledger failure writes neither. If your database standard routes every transaction through your own helper, pass it as `drizzleUsageSink({ db, transaction })`; every statement runs on the handle it gives the sink.
- **Only if you turn on `payloads`:** apply `sql/upgrades/0003-llm-call-payloads.sql` first (or install from `sql/install.sql`), and run `assertLlmCallPayloadsSchema(db)` at deploy or boot. The upgrade is one transaction with a transaction-local `lock_timeout`. If you already have a table named `llm_call_payloads` that is not exactly ours, rename it (with its index and foreign key) first: the upgrade stops with an error rather than write into a table of another shape. `payloads` without a `sink` is `bad_request` at `createClient`.
- **Stored payloads can contain customer data, and retention is yours.** The library never deletes them. Schedule `purgeLlmCallPayloads` and use `deleteLlmCallPayloads` for tenant or subject deletion; supply your own `redact` for personal data, since core's patterns cover credentials only.
- A custom `UsageSink` that wants payloads reads `record`'s optional second argument and declares `acceptsPayloads: true`.
